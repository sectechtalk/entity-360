1 What this is for

Entity 360 is a read-only identity investigation dashboard (Node.js), hosted on Azure Container Apps since October 24, 2026 (app-e360, image on ghcr.io) and still runnable on localhost for development. It reads Entra ID, Intune, Conditional Access, sign-in logs, licenses, billing and a Windows device snapshot, and shows each person only what their own roles allow. It is also a deliberate demonstration vehicle for the skills in the Senior Security Engineer, Identity and Access Management job description, and for the Microsoft SC-300 skills outline effective October 28, 2026.

Three design questions drive everything: how one sign-in reaches many sources, how a person is limited to the sources their roles permit, and how the same design later extends to an on-premises Active Directory and an on-premises site (version 2).

3 The three designs

The question: one sign-in (SSO) across many sources, with each person limited to the sources their roles permit. All three keep everything read-only.

Rank 1 Option 1: delegated sign-in, app roles for gating, governance around it

How it works. One registration holds delegated permissions to every API (Graph, Azure Resource Manager, Log Analytics, Defender). A server-side web app signs the person in once with authorization code and PKCE, as a confidential client with a certificate; no client secret. It then acquires a token per API silently. Each source is enforced by the viewer's own roles (Entra roles, Azure RBAC, Intune and Log Analytics roles). App roles (E360.Reader, E360.SignIns, E360.Intune, E360.Billing) are assigned through groups with "Assignment required" on, and the server checks them on every request.

Superseded in part (Oct 24, 2026). "One registration for everyone" is replaced: the existing "Entity 360" registration becomes the admin portal, and a new minimal "Entity 360 User" registration will serve end users. See section 13.

Strengths. Least privilege by construction; audit logs name the person; Conditional Access and MFA apply to the user's own token; smallest change from the code that exists.
Weaknesses. Depends on each viewer holding the right source roles; a source that offers no delegated route needs a different path (Option 2).

Rank 2 Option 2: hybrid, delegated first plus a narrow app-only broker

How it works. Option 1 for everything that supports delegated access. For unattended collection (for example a scheduled health snapshot) or a source with no delegated route, a small component reads with its own workload identity, with permissions limited to that source and its results gated by an app role. Never a silent fallback when delegated access is denied.

Strengths. Full coverage without broad app permissions; small blast radius; demonstrates application permissions and workload identity.
Weaknesses. Two security models to test and explain; the broker is a security boundary; audit logs show the app for those reads.

Rank 3 Option 3: app-only backend, Entity 360 as the authorization layer

How it works. The app holds application permissions to everything and decides in its own code who sees what; users sign in only to prove who they are.

Strengths. Simplest sign-in; independent of each user's source roles.
Weaknesses. Tenant-wide read in one app; any gating bug leaks everything; audit logs show the app for every read. Document it as the contrast ("why not"); do not build it.

Corrections adopted after review

  • A server-side web app uses a confidential client; PKCE does not replace its credential. A non-exportable Windows-store key needs a client-assertion signing integration that must be proven first.
  • "One sign-in" means one interactive sign-in; consent, MFA and Conditional Access challenges can still occur and must be handled.
  • App roles open features; the sources still enforce the viewer's own permissions. A hidden menu item is not authorization.
  • Administrative units demonstrate scoped administration; they do not hide objects from readers and do not scope Intune. Custom security attributes enforce nothing unless code or an ABAC condition reads them.
  • The Office 365 Management Activity API offers delegated and application permissions; it does not by itself force a broker.
  • Grant only the permission type the chosen model needs, even when an API offers both.
  • Never fall back silently to app-only access when delegated access is denied.

4 Data flow (Option 1, Phase 1)

The diagram shows the original localhost flow. Hosted (since Oct 24, 2026) the steps are the same: the server runs in Azure Container Apps, the callback is https://app-e360.example-00000000.westus3.azurecontainerapps.io/auth/callback, and the Key Vault token comes from the container's managed identity instead of the signed-in Azure CLI user.

Three gates on every call. (1) The registration lists the delegated permission; (2) an admin consented; (3) the signed-in person's own role allows the data. Conditional Access can challenge at any point. Steps 6 and 7 use the viewer's token, so Entity 360 never has more access than the person signed in.

Terms. PKCE = Proof Key for Code Exchange: the app sends a hash of a secret verifier first and must present the verifier to redeem the code, so a stolen code is useless. Nonce = number used once: a random value sent in the request and returned inside the ID token, binding the token to this sign-in. State protects the redirect back to the app.

Phase 2: governance, automation, source control

Exit test. Approving an access package grants the app role, the grant is logged, expires on schedule, and a leaver's sessions are revoked automatically with a run record.

Phase 3: hybrid AD and the on-prem site

  1. Environment. Build a lab domain controller (evaluation Windows Server on Hyper-V or similar); OUs, test users and groups with a routable UPN suffix. open decide hosting and licensing.
  2. Tenant change. Choose and deploy sync: Entra Connect Sync or Cloud Sync (compare against these scenarios), with password hash synchronization and Connect Health.
  3. Deliberately create sync problems (duplicate attribute, UPN suffix mismatch, scope filtering) and record the fixes in the journal.
  4. Join or hybrid-join a test device; decide between hybrid join and Entra join with cloud Kerberos trust.
  5. Environment. An on-prem IIS site with Windows authentication; install the Application Proxy connector; publish the site with pre-authentication and Kerberos constrained delegation.

  7. Add one SAML SSO enterprise application to complete the protocol set.

Exit test. A synced user signs in once, reaches the proxied site and Entity 360, and sees the AD facts they are allowed to see; a user outside the role gets nothing and the denial is logged.

7 Source control with GitHub

  • Repository. One private repository (or two: entity-360 and identity-lab-scripts). Keep it private; the tenant is real.
  • Never committed. Private keys (*.pem, *.pfx, *.key), .env, backup folders, snapshot JSON, tenant exports containing personal data. Extend the existing .gitignore accordingly.
  • Branch protection. Protected main, pull requests required, status checks required, signed commits optional.
  • Pull request template. Includes "Does this change the tenant?", "Which role or permission changes?", "Evidence attached", "Tests added".
  • Actions (CI). npm test and syntax checks; PowerShell parse check on every script; secret scanning with push protection; dependency review and Dependabot; CodeQL for JavaScript; PSScriptAnalyzer for PowerShell (CodeQL does not analyze PowerShell; see section 13).
  • Deploy without stored secrets. Use GitHub OIDC federated credentials to Azure for deploying the Logic Apps and infrastructure, and for the Action that uploads reviewed scripts to Intune (section 13); this is the exam's "federated credential" topic in practice.
  • Configuration as code. Commit sanitized read-only exports of Conditional Access policies, app registrations and role assignments; a scheduled workflow compares them with the tenant and opens an issue on drift.
  • Issues and project board. Track the phase tasks and open items so the plan is visible and dated.

Creating the repository and pushing is outward-facing: it needs your explicit go. The existing C:\src repository reports "dubious ownership" for this user, which must be understood before any commit. 9 Secrets and Azure Key Vault

Decision (October 12, 2026): use Azure Key Vault. At lab volume it costs cents per month (about USD 0.03 per 10,000 operations, reported), so it is accepted as the one deliberate paid exception. Everything else stays at zero cost. The Windows certificate store with a local signing helper remains the free fallback if the cost ever stops being acceptable.

Goal. Keep as many secrets as possible in Key Vault, with one vault per component so a compromise or an access change stays small. The design has very few secrets to begin with: no client secret is used, and the only long-lived credential is the app's certificate key.

Vault (proposed name pattern)HoldsWho or what reads it

Vault names are global and 3 to 24 characters, so adjust the pattern. Practices to apply: Azure RBAC authorization instead of access policies, soft delete and purge protection on, diagnostic logs to Log Analytics, separate vaults per environment (lab and any later production), and least privilege per identity (for example "Key Vault Crypto User" for signing only; "Key Vault Secrets User" for reading a secret).

The "secret zero" problem. Something has to authenticate to Key Vault without a secret: on this computer the server uses the signed-in person's Azure login; the hosted app (Container Apps, since Oct 24) uses its system-assigned managed identity with Key Vault Crypto User on the key only; CI would use GitHub OIDC federation. Each is a different answer to the same question, and it is worth saying so out loud in an interview.

Key handling. Primary: a certificate created in Key Vault with a non-exportable key; the server asks Key Vault to sign the JWT assertion (a "sign" operation) and hands the result to the MSAL client-assertion callback, so the key never appears as a file. Fallback: a non-exportable key in the Windows certificate store with a local signing helper (free). Last resort while the integration is proven: a key file with a restricted ACL. This signing integration is the proof task ChatGPT asked for.

Consequence to accept. Purge protection cannot be turned off once enabled, and a deleted vault keeps its name reserved for the retention period. Plan vault names and cleanup accordingly.

Why Logic Apps can get expensive, and how this design avoids it

Verified against Microsoft Learn (usage metering, billing and pricing for Azure Logic Apps, July 2026).

  • Standard plan reserves compute. You pay for the hosting plan whether or not workflows run. Learn's worked example (an illustrative region) gives about USD 175 per month for the smallest tier (WS1, 1 vCPU, 3.5 GB), 350 for WS2 and 700 for WS3. This is the usual cause of "Logic Apps was expensive".
  • Consumption bills per execution, with an initial free allowance of built-in operations per subscription. Polling triggers are billed every time they check, even when they find nothing: a one-minute poll is about 43,000 trigger executions a month.
  • Loops and retries multiply cost: a "for each" over 10 items is 11 executions; an action with 5 retries is billed as 6.
  • Managed connectors are billed from the first call (Standard or Enterprise connector rates); built-in operations are the ones covered by the free allowance.
  • Run-history retention storage is billed separately.

Rules for this lab: Consumption plan only; event or recurrence-by-hour triggers, never frequent polling; built-in actions and HTTP calls to Graph where possible; no loops over large lists; retries set low; keep one workflow active at a time; set a budget alert (it notifies but does not stop spending, so disable the workflow when finished). Exact per-action rates are not shown on the captured pricing page: check the Azure pricing calculator before building.

Cost traps and availability corrections

  • Free control plane is not free infrastructure: AKS, Batch, Service Fabric, Machine Learning, VM Image Builder, DevTest Labs, Deployment Environments and migration tools can provision or use billed compute, storage and networking. Do not deploy these for Entity 360 merely because the coordinating service is free.
  • Private Link: the service component can be free; private endpoints and processed traffic are billed. Avoid them for the initial local demonstration. Microsoft details.
  • Cloud Shell: use ephemeral sessions for no persistent-storage bill. Mounting Azure Files incurs storage charges. Microsoft details.
  • Arc and Update Manager: Arc's base control plane does not make its add-on services free. Update Manager's free Azure VM treatment does not apply universally to Arc servers.
  • Log Analytics: its shared 5 GB allowance does not make Sentinel, all log-table plans, custom metrics, alerting, export or extra retention free. Limit diagnostic categories instead of collecting every Windows event.
  • Catalog errors: Content Safety incorrectly lists an AKS quota. Other pages disagree about some quotas and naming. Product-specific documentation takes precedence.
  • B2C: unavailable to new customers since May 1, 2025. Use an appropriate modern identity option; do not build this workforce dashboard around a legacy catalog entry. Microsoft details.
  • Legacy / retirement planning: Data Catalog documentation is archived under previous versions. Automanage Best Practices retires September 30, 2027; Custom Vision retires September 25, 2028. Do not add these to Entity 360's foundation. Microsoft details; Microsoft details.
  • SQL Managed Instance: its separate free offer lasts 12 months from activation and stops afterward; unlike the ongoing SQL Database offer, it is not a long-term free database choice. Offer details.
  • Identity licensing: Conditional Access, PIM and advanced Governance need appropriate premium licenses. Graph sign-in-log downloads need Entra P1/P2. Intune and Defender source access also depends on relevant licensing and authorization. Basic SSO or a free host does not remove those requirements. Microsoft details; Microsoft details.
  • Budget alerts: notify; they do not stop consumption. Use free SKUs with enforced caps where possible, plus carefully chosen policies and explicit opt-in for paid additions. Microsoft details.

13 End user and admin split, device tests, and the script pipeline (agreed Oct 24, 2026)

Registration decision (Oct 24, 2026). The existing live registration "Entity 360" (appId 00000000-0000-4000-8000-0000000000a3) becomes the admin portal and keeps its scopes, app roles, Conditional Access and redirect URIs. A new, separate, minimal registration "Entity 360 User" is created later for the user portal. Neither change has been made yet.

Goal

Same data, two audiences. End users run diagnostics as themselves with minimal rights and answer one question: can I actually reach the shares, sites and apps I should? Admins see all of Azure plus who is granted access to each share, site and app. Admins can also request tests that run as the user, on the user's device.

Three parts, one shared data model

User portal

A new registration, "Entity 360 User" (plan step 4.2, tenant change, not created). Uses the signed-in user's own token only, with delegated User.Read and only what end-user self-diagnostics need. It shows what the user is expected to have against what actually works. It contains no admin code paths.

Admin portal

The existing "Entity 360" registration and the hosted app-e360, keeping its broad delegated read scopes and four app roles. Plan step 4.1 hardens it: Conditional Access requiring MFA and a compliant device, and PIM-gated app roles. It shows the full Azure and access view, and it is where device tests are requested.

Device agent through Intune Remediations

Detection scripts run as the logged-on user. Their output (JSON, kept under about 2,048 characters) is read through Microsoft Graph at deviceHealthScripts/{id}/deviceRunStates, field preRemediationDetectionScriptOutput. Remediations require Windows Enterprise E3/E5 rights, which Microsoft 365 E7 covers. Custom compliance scripts are the option when a failed check should block access through Conditional Access. Plain Intune platform scripts return no readable output, so they are not used for this.

Local collector ("Collect this computer"). Works only when the browser and server run on the same PC (localhost). In the hosted app it would read the container, so snapshot import is the hosted fallback. Intune Remediations are the target design for device data.

No impersonation

Admins never hold a user's token. "Test as user" means the admin requests a test, Intune runs the reviewed script in the user's context on their device, and the result returns to the admin portal with the requester, time and reason recorded for audit. Entra does not let admins mint user tokens, and literal impersonation would fail an audit.

Why split

The user side is low-privilege; the admin side holds powerful tokens. If both shared one app and one session store, a bug in the user view could become an admin breach.

Timing, accepted

Remediations run on a schedule, hourly at best. A single-device run-now still takes minutes. The owner accepted this. A persistent real-time agent on the device was rejected because of its larger attack surface.

Script pipeline

Script, then GitHub pull request, then PSScriptAnalyzer (including its security rules) in a GitHub Action on every pull request (enforcing it as a required check is open decision (b) below), then merge, then a GitHub Action uploads the script to Intune through Microsoft Graph. That Action authenticates with GitHub OIDC workload identity federation to Entra, so no secret is stored, and its permissions are limited to Intune script management (an application permission; open decision (a) below). Intune then runs the script on devices and e360 reads the results.

GitHub is the source of truth. Intune never fetches from GitHub itself; it holds its own copy uploaded by the Action. CodeQL does not analyze PowerShell, so PSScriptAnalyzer is the gate. GitHub Copilot code review (a separate license, not part of Microsoft 365 E7) is optional later as a second opinion, not a gate.

First example device check

Network connectivity: DNS resolution, Test-NetConnection against a few targets, and latency. The script prints one line of JSON and exits 0 when healthy, 1 when there is a problem.
