1. Start the dashboard

Requires Node.js 22 or later. The project lives in C:\path\to\entity-360.

cd C:\path\to\entity-360
npm ci
npm start

Open http://localhost:3600. You can also run Start-Entity360.ps1 from the project directory. Demo mode includes two users, one application, one managed identity, and two viewer permission profiles.

The server listens only on the local loopback interface. It is not configured for shared hosting. Stop a foreground instance with Ctrl+C. A background instance started during development records its process ID in .runtime\server.pid; use Stop-Entity360.ps1 to stop that instance.

2. Register a public-client application

  1. In Microsoft Entra admin center, select your tenant, then App registrations → New registration.
  2. Name it Entity 360 Local and select accounts in this organizational directory only.
  3. Copy the Directory (tenant) ID and Application (client) ID.
  4. In Authentication → Advanced settings, enable Allow public client flows. Device-code sign-in does not need a redirect URI or a client secret.
  5. Add only the delegated permissions you intend to use from the table below. Arrange administrator consent where required. The viewer must also have the relevant service roles, resource scopes, and licenses.

Microsoft’s device-code sign-in documentation describes this flow. If your tenant blocks device-code authentication, this local release needs an authentication-flow change; do not weaken the tenant’s policy to run it.

notepad .env

Set the two IDs, adjust GRAPH_SCOPES to the delegated permissions granted to this application, then restart the server:

ENTRA_TENANT_ID=your-tenant-guid
ENTRA_CLIENT_ID=your-app-client-guid

In the dashboard, open Connection & setup → Sign in with Microsoft. Use the verification link and displayed code. Once signed in, search for your entity. Tokens and the MSAL cache remain in server memory and are discarded when the server stops or you sign out locally. Local sign-out does not sign you out of Microsoft in other browser tabs.

4. Optional workspace telemetry

Configure up to five Log Analytics workspace GUIDs in .env, restart, and use Connect workspace logs after Microsoft sign-in.

LOG_ANALYTICS_WORKSPACE_IDS=workspace-guid-1,workspace-guid-2

Workspace logging and ingestion must already be enabled. This app does not create diagnostic settings, connectors, or instrumentation. The following tables are queried independently and appear only after an authorized successful query:

  • MicrosoftGraphActivityLogs: API calls matched to user ID, service-principal ID, or app ID.
  • OfficeActivity: collected Microsoft 365 audit actions matched to the selected user’s UPN or object ID.
  • AppRequests and AppDependencies: instrumented application requests and downstream calls. User investigations match UserAuthenticatedId to object ID or UPN. Your instrumentation must populate this field consistently.

For workload identities, configure an explicit mapping from a service-principal object ID to the instrumented application role names:

TELEMETRY_ENTITY_ROLES={"service-principal-object-guid":["finance-api","finance-worker"]}

This mapping associates telemetry with the selected application; it does not prove which identity or credential made each request. Operation IDs are preserved to support correlation. Tokens, secrets, and credential values are never required in this mapping.

Source links open Log Analytics, with a copyable query and workspace ID in View evidence. Microsoft documents Log Analytics authentication and the Graph activity table.

Coverage, authorization, and operational limits

  • Successful query results establish source visibility. Denied sources are not sent to the browser. All requests use the current session’s delegated tokens. Sources returning errors are not presented as empty successful results.
  • Records and queries stay in memory for the request; CSV export is explicit. Sessions expire after eight hours of inactivity. Session cookies are HttpOnly and SameSite=Strict. Host, origin, fetch-site, and CSRF checks protect the local API.
  • Maximum timeframe: 90 days. Default page cap: 10 pages per endpoint; configurable with MAX_PAGES, capped at 50. Role inheritance checks cover at most 24 direct groups. Azure scans at most 10 subscriptions. Intune per-policy queries cover at most 10 devices. Workspace queries and Defender hunting return at most 1,000 rows each.
  • Limits and query failures mark results partial. Retention, licensing, disabled logging, sampling, and instrumentation can still omit activity even when every query succeeds. Current configuration does not establish what was configured at an old event.
  • Portal routes can change. Where exact event deep links are not reliable, the UI labels the link as a source view and supplies the record ID, correlation ID, timestamp, or query. Policy and object links use the corresponding portal routes and still need tenant verification.
  • Demo rows are intentionally fictional. Portal links in demo mode do not point to real records. Switching a demo viewer is not a Microsoft permission change.
  • This release targets Microsoft’s global commercial cloud. Sovereign cloud endpoints and shared-hosting deployment are not configured.

Validation and next connection step

Tenant boundary and identity model

A person may authenticate into several organizations through a home identity, B2B guest/member objects, or distinct organizational accounts. Licenses can be assigned to eligible directory objects in different tenants, subject to the service’s licensing/support rules. Guest access by itself does not mean a guest has a local SKU assignment or needs one. A personal account used to authenticate a tenant guest remains separate from the personal consumer subscription; these contexts are not merged.

Keep a tenant boundary for every query and authorization decision. Entity 360 keys organizational contexts by tenant ID plus local directory object ID, keeps MSAL state/resource connections within that context, and snapshots token context at the start of each request. Same email/name does not merge contexts. Switching clears displayed investigations and local imports; sign-out clears all server-memory connections. Cross-tenant overview can later compare explicitly connected contexts, but must never pool seats or infer license portability.

Use the view

  1. Open Licenses → Connect or switch account. For an organization, enter its tenant GUID and sign in. For a personal identity choose Sign in with personal Microsoft account.
  2. Complete Microsoft sign-in and the applicable authentication challenge. Choose Check licenses. Level 1 is the signed-in identity; Level 2 appears only if an authorized tenant inventory query succeeds.
  3. For another organization, connect it independently. Use the connected account/tenant selector to activate a previously connected context. There is no automatic discovery or silent authentication to all organizations.
  4. For consumer subscriptions, open Services & subscriptions with the intended account. Record the product and whether you own it or receive a shared benefit if useful. Export license evidence to preserve provenance and timestamps. User-reported notes are browser-memory-only and clear on account/profile switch.

Cross-tenant licenses and Billing: October 11, 2026

User requested all licenses for the signed-in principal, tenant discovery, and Billing across accessible tenants/subscriptions. Navigation now places Licenses immediately after Source coverage, followed by Billing.

Current user across tenants

Licenses defaults to All connected tenants for this principal. The server selects only authenticated contexts sharing Microsoft’s homeAccountId with the current principal; same email or display name never merges different accounts. Each license query uses the context’s own Graph token, tenant and directory object. The active context is not switched by a portfolio scan. Results show each tenant’s products and service statuses, plus authorized tenant inventories.

Discover other tenants queries Azure Resource Manager /tenants after an explicit Azure connection. ARM-visible tenant IDs are validated. Up to 20 directories are considered. With ALLOW_MULTI_TENANT=true and a compatible app registration, cached delegated consent is used to attempt silent Graph authentication in each directory; a valid returned tenant/local account and identical home-account identifier are required. Azure silent access is separately attempted and validated. Missing consent/MFA/cache is labeled sign-in-or-consent-required; no interactive authentication storm or license-assignment change is performed. The connection selector refreshes after discovery.

Completeness is not established: ARM-visible directories are not a universal list of Microsoft relationships. Unconnected/undiscovered tenants and consumer subscriptions remain unknown. Tenant sign-in does not prove license-reading privileges. Failed license queries are distinct from successful zero-assignment results. These boundaries remain visible in the cross-tenant coverage table and exported evidence.

Use and limits

  1. Configure the existing public-client app and appropriate read consent. Enable multi-tenant mode only with a compatible audience.
  2. Connect Microsoft and Azure under the same organizational account/tenant. Open Licenses → Discover other tenants. Connect directories requiring explicit sign-in via Connection & setup.

Limits: configured upstream page cap; 20 discovered directories; 30 subscription cost scopes; 20 management groups; 30 resource groups per fallback subscription; 20 billing accounts, 20 profiles per account, 20 invoice sections per profile; 50 cost and 50 budget queries per context; cost response cap of 100 rows with partial-result flag. Excess or denied/unsupported queries mark results partial. The API page cap is not an assertion of complete history.

Still not implemented: consumer billing retrieval; complete Microsoft 365 invoices/payment data; Partner Center/CSP invoices; GitHub/Visual Studio billing; savings-plan/commitment detail; arbitrary billing-role-only scope discovery when parents are not listable. Accessible items in these surfaces require additional connectors and permissions. The interface therefore reports authorized collected evidence and coverage gaps, not a claim that every item visible in every Microsoft portal was retrieved.
